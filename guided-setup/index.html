    Guided setup: hound init and hound add¶

    hound can write a compliance repo's files for you. hound init scaffolds a new organisation, and hound add adds a system, a control or a collector. Each asks only the questions it needs, shows the default in brackets (press Enter to take it), and checks the result the way hound config validate and hound scope validate do before it writes anything. A change that would not validate is not written: hound reports the problems, with exit code 3, and leaves the files as they were.

    Every question has an option, so a wizard also runs unattended: give the answers as options and add --yes, and it asks nothing, taking the defaults for anything not given. Questions go to stderr, so the output stays clean.

    The local trial uses these wizards from start to finish.

    hound init¶

    hound init compliance

    Writes a new compliance repo into the folder, which must be missing or empty:

    Question Option Default
    Organisation name, also its domain in CISO Assistant --org Example Pty Ltd
    Short code for ref IDs, such as EX in EX-E8-Q2-2027FY --code from the name
    CISO Assistant API address --url https://ciso.example.com/api/
    Time zone schedules run in --time-zone Australia/Sydney
    Essential Eight maturity level to assess, 1 to 3 --level 2
    Audit interval: each quarter of the financial year (July to June), or each month --interval quarter
    Compliance owner's email --owner ceo@example.com

    --evidence-root sets where the runner keeps evidence (default /var/lib/evidence-hound/evidence, outside the repo; only root or the runner container can write there, so for a trial as yourself use a folder in your home, such as --evidence-root ~/hound-evidence).

    Audits are per system, so each shows its own gaps: hound init writes no organisation-wide audit. It names the series each system's audit joins (<CODE>-E8, so EX-E8-SOPHOS-NETWORK, by quarter or month) in scope/setup.yaml, and hound onboard <system> drafts the system's audit in it. --organisation-audit also writes one Essential Eight audit for the whole organisation: only when an organisation-wide source, such as policies, feeds it. --framework disp also writes a DISP membership readiness audit (DISP readiness), which is organisation-wide by nature. Neither is asked.

    It writes:

    File Holds
    hound.yaml The deployment config: CISO Assistant, evidence, the schedule's time zone, no collectors yet, and no targets until an audit is approved (hound approve adds a system's audit's target once the repo has that system's mapping, mappings/<system>-<framework>.yaml)
    scope/setup.yaml The root folder and the audit series (audit_series: its ref ID, maturity level and periods), the Essential Eight framework with its snapshot, and one domain with its perimeter
    scope/controls.yaml The health control, AC-AUTO-EVIDENCE
    scope/access.yaml The compliance owner as a user, and the GRC team they lead
    scope/evidence-plan.yaml, manual-sources/weekly-compliance-review.md The weekly review: a task for the GRC team every week, whose runbook says how to start hound review (the weekly review)
    scope/audits/README.md How audits are drafted: one per system and per shared platform. With --organisation-audit, also scope/audits/<code>-e8.yaml: the series <CODE>-E8 at that maturity level for the whole organisation, with its target and health control in hound.yaml. Each period is its own audit, such as EX-E8-Q2-2027FY (Audit periods)
    mappings/essential-eight-2023.yaml, frameworks/essential-eight-2023.json The Essential Eight mapping and framework snapshot of this hound version
    With --framework disp: frameworks/disp.yaml, frameworks/disp.json, mappings/disp.yaml, scope/audits/<code>-disp.yaml The DISP library, its snapshot and mapping, and the audit series <CODE>-DISP, declared in scope/setup.yaml and added to targets in hound.yaml
    .devcontainer/ The GRC team's workspace: released hound, the .NET runtime and the Claude Code and GitHub Copilot extensions, so your machine needs only Docker and VS Code (work in the devcontainer)
    .gitignore, README.md What never goes in the repo, and the next steps

    For more people, settings and a pull request workflow, copy them from the example compliance repo, as the first deployment tutorial describes.

    At the end hound init asks whether to set up a coding assistant in the new repo (claude, copilot, both or none; --assistant answers it, and --yes takes none). With every answer given as an option nothing is asked, and --json answers with the organisation, the audits it wrote (audits, empty by default) and every file written, for an agent. It writes what hound agent setup writes.

    hound add system¶

    hound add system --scope scope --audit EX-E8

    Adds a system to a domain in scope/setup.yaml: its name, ref ID (default SYS- and the name), type (primary or supporting), owner, description and the systems it supports, by name (--name, --ref-id, --type, --owner, --description, --parents "Example 365"). The domain is asked only when the scope has more than one (--domain). Each --audit adds the system to that audit's systems.

    hound add control¶

    hound add control --scope scope --audit EX-E8

    Declares an applied control in scope/controls.yaml: its ref ID, name, owner, category (default technical) and the systems it covers (--ref-id, --name, --owner, --category, --systems), with status to_do until the first apply. With --audit, it asks which of that audit's requirements the control supports (--requirements ISM-1511,ISM-1515) and links them in the audit file. A requirement the framework does not have is refused.

    hound add collector¶

    hound add collector manual --config hound.yaml
hound add collector rest --name sophos --set profile=sophos-central --config hound.yaml --secrets-dir /etc/evidence-hound/secrets

    Adds a collector of any type hound collectors list lists. It asks for the collector's name (default: the type), its schedule (default 0 3 * * *) and each setting the collector requires, using the collector's own description of it. --set key=value gives any setting, optional ones included, without asking. For the rest collector, once it knows the profile (--set profile=<name>, and --set profiles_path=<folder> when the profiles folder is not the default), it also asks for each parameter the profile requires and has no default for, and takes the profile's secrets as the collector's.

    For each secret the collector needs:

    • Without --secrets-dir, it asks for a reference, by default file:/run/secrets/<name>_<secret>, the path the runner container sees. Put the value in that file on the host yourself.
    • With --secrets-dir <folder>, it reads the value instead, without echo on a terminal, writes it to <folder>/<name>_<secret> (folder mode 700, file mode 600) and references that file. The value is never printed, logged or put on a command line.

    hound add collector manual is how a manual evidence source is added: its drop folder, the checks it supports, how often fresh evidence is due and who owns it. See manual sources.

    How the files are changed¶

    An added entry goes at the end of its list, in the file's own indentation. Comments, blank lines and every other line stay as they were, so the change reads as a small diff in review. An empty [] list becomes a block list, and a missing list is added. Values are quoted only where YAML would read them as something else, such as "0 3 * * *" or "14".
