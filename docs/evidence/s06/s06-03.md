# s06-03 Several audits from one run

**Status:** Done (2026-11-21).

## What was done
- Config: `targets:` is a list, and each target names a mapping, an audit and its controls (with an optional health control). A single `target:` is still accepted and read as a one-item list. Problems: `config.targets_conflict` (both keys), `config.targets_empty`, `config.targets_not_a_list`, `config.target_duplicate` (two targets for one audit). `schemas/config.schema.json` accepts exactly one of the two keys. `docs/configuration.md` has a targets section.
- Planning: `AuditPlanner.PlanUpdates(IReadOnlyList<TargetResults>, evidence, controlStatuses)` uploads each piece of evidence once (by ID), then sends requirement updates audit by audit in target order, then one update per applied control however many targets configure it. A control key is known if any target configures it. The single-target overload delegates to it.
- Runtime: `Runner` takes a list of `RunTarget` (mapping, audit target, health control). Each target gets the results its mapping owns; the health evidence is linked to every distinct health control.
- Report: `PublishReport.Audits` gives planned, sent, skipped and failed per audit. `hound publish` and `hound run` print them under `audits`, and each item's note. Every item is attempted, so a failure in one audit does not stop the next.
