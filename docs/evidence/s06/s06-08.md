# s06-08 Scope apply: domains, perimeters and systems

**Status:** Done (2026-11-21).

## What was done
- `ScopeApplier.ApplyAsync` (core) carries out a plan in its order through an `IScopeWriter`, for the kinds this version applies (domains, perimeters and systems); changes of other kinds are counted as not applied. A change whose domain, parent system, perimeter, framework, system, document or audit failed or was skipped is skipped too, so a failed write stops only its dependants. The report gives each change's outcome and detail.
- `ScopeWriter` (CISO Assistant adapter): a domain is a folder under the root folder (`content_type: "DO"`), a perimeter sits in its domain, and a system is an asset with its type, parents and owners. Each write finds the IDs it needs by name first, so nothing is sent when a name cannot be resolved. Each object's description ends with the `[hound scope <state>]` marker.
- Owners are actors: CISO Assistant v4.3.4 keeps owners, authors and reviewers as actors (one per user, team or entity), not users. The writer sends each owner's actor ID, found from the user's email; the reader names an actor by its user's email, or by its own name for a team or entity. The inventory snapshot now includes `/api/actors/`.
- `hound scope apply <dir> [--config] [--dry-run] [--prune]` validates first and writes nothing when the scope has problems. `--dry-run` prints the plan. The report is JSON (`written`, `failed`, `skipped`, `not_applied`, each change); any failure exits with code 4.
- The dev seed creates the example staff users the scope names as owners, authors and reviewers.
- `docs/scope.md` has an Apply section.
