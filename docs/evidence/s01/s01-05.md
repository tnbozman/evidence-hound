# s01-05 Audit update plan

**Status:** Done (2026-11-21)

## What was done
- `src/EvidenceHound.Core/Planning/`: `AuditUpdate` is a closed set (private constructor) of `UploadEvidence`, `UpdateRequirementAssessment` and `UpdateAppliedControl`, with a `Match` over the three cases. `AuditTarget` holds the audit ref_id and control key to ref_id map from config. `ControlStatus` and `ControlState` (CISO Assistant's `to_do`, `in_progress`, `on_hold`, `active`, `deprecated`).
- `AuditPlanner.PlanUpdates(target, requirementResults, evidence, controlStatuses)` is pure. Order: evidence uploads (by ID), then one requirement update per result (in result order), then control updates (by key).
- `DispatcherMessages.ToJson` writes each update in the dispatcher message shape, checked against the upstream dispatcher README and `messages.py` (`message_type`, `selector`, `values`). The file content comes from a function, so the core stays free of I/O.
- CLI: `hound plan --dry-run --config <yaml> --checks <json>`. The config gains a `target` section (mapping path relative to the config file, `compliance_assessment`, `controls`). The check results file gains optional `evidence` and `control_statuses`.
- Docs: [`docs/audit-plan.md`](../../audit-plan.md).

**Deviations from the plan, all recorded under "Discovered work":**
- `PlanUpdates` returns `Result<IReadOnlyList<AuditUpdate>>`, not a bare list, so a result citing unknown evidence or an unconfigured control key is a returned problem rather than a silent drop or an exception.
- `values.evidences` carries evidence `ref_id`s. CISO Assistant's API expects evidence IDs there, so the s02 publisher must resolve them.
