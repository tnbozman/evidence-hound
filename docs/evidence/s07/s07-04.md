# s07-04 Users, teams and roles as configuration

**Status:** Done (2026-11-22).

## What was done
- **`scope/access.yaml`** lists users (email as the key, names, `active`, `service_account: publish | apply | true`), teams (domain, leader, members) and roles (a built-in or custom role on a domain, for users and teams). JSON schema, example, and a section in the scope guide.
- **Validation**: duplicate or malformed emails (with the line of the first one), unknown roles, domains, users and teams, and any domain with no active approver on it or on `Global` (`access.domain_without_approver`). A password, token or secret key anywhere in the file is `scope.secret_in_file`, and the value is never shown.
- **Roles are user groups.** CISO Assistant v4.3.4 lets no one create role assignments through its API: administrators only view them, and CI got HTTP 403 on every POST. A role on a domain is membership of that domain's built-in group for the role, for example "Example Pty Ltd - Approver". So each user's roles, given directly or through teams, are one field of the user (`roles: BI-RL-ADM on Global, BI-RL-APP on Example Pty Ltd`). Apply sets the user's `user_groups` to exactly those groups, and a role removed from the file is taken away on the next apply. A folder made through the API gets those groups only with `create_iam_groups: true`, which hound now sends for every domain. CISO Assistant lists built-in roles and groups by their translated display name (BI-RL-AUD is "Reader"), so hound asks for English and maps the names back to codes.
- **Users are never deleted**: `--prune` deactivates a user who was removed from the file. hound never sets or reads a password, and new users get CISO Assistant's invitation.
- **Access review** in `scope plan`: active people without MFA, and any `publish` service account that holds more than analyst, however the role was given. MFA cannot be required per user. Set `enforce_mfa` in `settings.yaml` instead (s07-05).
