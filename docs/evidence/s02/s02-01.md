# s02-01 Local CISO Assistant for tests

**Status:** Done in code and CI (2026-11-21). The manual browser check needs the maintainer (steps below).

## What was done
- `dev/ciso-assistant/compose.yml`: CISO Assistant backend and frontend pinned to `v4.3.4`, SQLite in the named volume `ca-db`, Caddy with an internal certificate on `https://localhost:8443`. `make ca-up` starts and seeds it; `make ca-down` stops it (`ARGS=-v` deletes the data).
- `dev/ciso-assistant/seed/`: `seed.sh` runs inside the backend container. It loads the Essential Eight library and a fictional "Example baseline" library, creates the service account `hound-service@example.com` in the administrators group with a 30-day personal access token, and creates the folder "Example Pty Ltd", the perimeter "Example baseline", the audit `EXAMPLE-BASELINE-2026` and the applied controls `AC-MFA` and `AC-BACKUP`. It is safe to run again.
- `scripts/ca-seed.sh` writes `HOUND_CA_URL` and `HOUND_CA_TOKEN` to `.dev/ca.env` (git-ignored, mode 600). `scripts/ca-secret-key.sh` generates the Django secret key once into `.dev/ca-secret-key`.
- `tests/EvidenceHound.Functional.Tests/CisoAssistantFixture.cs`: the same image and seed through Testcontainers, shared by the `CISO Assistant` collection. It passes a random superuser password and secret key, and shows the container log tail if the backend never becomes healthy.

## Deviations
- The superuser is created by the image from `DJANGO_SUPERUSER_EMAIL` / `DJANGO_SUPERUSER_PASSWORD` (`admin@example.com`); set `HOUND_CA_ADMIN_PASSWORD` before `make ca-up` to choose the password.
- The backend's own secret key generation produced an empty key in CI, so both the fixture and compose now pass `DJANGO_SECRET_KEY` explicitly.
- This cloud dev box cannot pull CISO Assistant images (ghcr blob storage is blocked), so the CA functional tests were run in CI only.
